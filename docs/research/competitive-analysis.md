# Исследование: docs↔код аудит + конкурентный ландшафт aiTelegaBot

Дата: 2026-09-04.

## Методология и её честные ограничения

Исследование выполнялось двумя независимыми треками:

1. **Docs↔код аудит** — один Opus-субагент по методологии `.claude/skills/code-docs-audit`
   (6 частей: A–F, только отчёт, без правки доков — по явной просьбе), затем 3 находки
   перепроверены вручную (file:line) в основной сессии.
2. **Конкурентный ландшафт** — фоновый Workflow (6 сегментов поиска × discovery →
   deep-profile → applicability → adversarial-verify), затем ручное восстановление пробелов.

**Что пошло не по плану, и как это исправлялось (прозрачно, без замалчивания):**

- Первый прогон Workflow (135 агентов, ~3.2M токенов) упёрся в rate-limit провайдера:
  из 51 уникального (по имени) найденного продукта только 34 получили профиль, из них
  только 5 — полную оценку применимости.
- Resume-прогон (121 агент, ~1.26M токенов) уткнулся в **лимит сессии** — часть уже
  готовых результатов при этом не переиспользовалась из кеша (движок resume оказался не
  полностью устойчив к параллельному порядку вызовов внутри `pipeline()`), итог стал
  *хуже* по числу продуктов с applicability (0 новых, 6 продуктов из первого прогона
  временно потеряны при мёрдже, восстановлены обратно вручную).
- После сброса лимита пробелы (17 продуктов без профиля вообще, 29 без applicability)
  закрывались вручную: применимость для профилированных-но-неоценённых продуктов
  оценена **мной напрямую** в основной сессии (аналитическая задача на уже собранных
  данных, без нового агента), а 16 полностью пропавших продуктов профилированы 4
  параллельными Agent-вызовами (≤4 одновременно, без вложенных субагентов, каждый —
  напрямую через WebSearch/WebFetch без делегирования).
- При объединении обнаружилось, что 3 продукта были найдены **дважды под разными
  именами** в разных заходах (`RSS-to-Telegram-Bot` = `telegram-rss-bot`; `RSSbrew` =
  `rss-digest`; `TLDR Newsletter` = `TLDR Tech/TLDR AI`) — ниже они объединены в один
  раздел с пометкой об этом.
- Итог: **48 уникальных реальных продуктов** с профилем и применимостью (из 51
  найденных по имени кандидатов, за вычетом 3 склеенных дублей).
- Claim о существовании официальных Claude-скиллов (`gopls-lsp`, `claude-md-management`,
  `hookify`) перепроверен вручную через `gh api repos/anthropics/claude-plugins-official`
  — все три подтверждены реальными пунктами списка плагинов.

Везде, где уверенность агента в конкретном факте (цена, лицензия) отмечена как
`medium`/`low` в первичных данных — это перенесено в текст явно; такие цифры — снапшот
на дату исследования (сентябрь 2026), не гарантированно текущие. Полные необрезанные
JSON-данные исследования (все features/pros/cons/sources) сохранены в scratchpad сессии,
в отчёт вынесена сфокусированная выжимка.

## Часть 1 — Docs↔код аудит

Полная методология: `.claude/skills/code-docs-audit`. Ниже — находки субагента,
верифицированные вручную (3 из них перепроверены по file:line лично).

### A. «Готово» в доках vs код

**Фаза 2 (MTProto) полностью реализована в коде, но нигде не помечена как done.**
`internal/mtproto/` содержит `client.go`, `session.go`, `source.go` + тесты (7 тестовых
функций), подключено в `app.go:87-110` (git-коммиты этапов 6–7). При этом
`docs/TECHNICAL_PLAN.md` §9 (строки 245–321) и `docs/PLAN.md` §6 (113–129) описывают
Этапы 0–7 без единого статус-маркера — читатель не может понять из живых доков, что
весь MVP плюс `/addsource` уже в проде. **Подтверждено вручную** — читал `TECHNICAL_PLAN.md:295-322`
лично: заголовки "Этап 6", "Этап 7" идут без пометок готовности, при этом
`internal/mtproto/` реально существует и наполнен кодом.

Точечные проверки, которые **подтвердились** без расхождений: retry `429→200` тест
(`internal/llm/retry_test.go:22`), идемпотентность слота планировщика через `meta`
(`scheduler.go:139-161`, `app.go:232-239`), детерминизм offline-суммаризатора.

### B. Командная поверхность (аналог producer→consumer для этого проекта)

**`/addsource` и `/removesource` подключены и работают (`router.go:75-78`,
`source_admin.go`), но отсутствуют в таблице команд README.md.** Таблица (строки 88–93)
перечисляет только `/start /help /digest /sources`. **Подтверждено вручную** — читал
`README.md:85-95` лично: таблица действительно останавливается на четырёх командах, хотя
в коде их шесть. Топ-строка README (строка 17: "Команды бота: `/digest`... `/sources`")
той же болезнью.

### C. Согласованность доков

1. **Расхождение версии Go.** `go.mod:3` = `go 1.25.0`, `Dockerfile:7` = `golang:1.25`
   (обновлено в `4859033`), но `TECHNICAL_PLAN.md:18,30,228` и `PLAN.md:61` всё ещё
   говорят "Go 1.22+" / `golang:1.22`.
2. **Дерево файлов в `TECHNICAL_PLAN.md` §3 устарело** (строки 52–89): называет
   `feed/hackernews.go` (реально `feed/hn.go`), `llm/summarize.go` (реально `prompt.go`),
   `telegram/commands.go` (реально `router.go`+`source_admin.go`) и т.д. — не отражает
   фактическую структуру `internal/`.
3. Нумерация секций и внутренние ссылки (§4, §5, §7, §9) — без разрывов, ок.

### D. Готовность нереализованных планов к передаче агенту

Не применимо в ожидаемом виде: единственная "Фаза 2", которая могла бы требовать
доуточнения, уже полностью реализована. Остальные пункты `POST_MVP_PLAN.md` корректно
оформлены как пул нерешённых nice-to-have (не роадмап), тянуть их к "implementation-ready"
преждевременно. Одно реально открытое решение, оставленное пользователю как есть:
per-channel буферизация для нескольких `tg_botapi`-источников (см. E ниже).

### E. Полная развёртка `docs/`

Файлы (проверено `find` вживую): `TECHNICAL_PLAN.md`, `PLAN.md`, `POST_MVP_PLAN.md`,
`plans/feat-dynamic-sources.md`, плюс `.claude/skills/go-telegram-bot-dev/SKILL.md`.

1. **Незанесённое в живые доки:** `docs/plans/feat-dynamic-sources.md` §10.1
   (строки 711–718) документирует нерешённое ограничение — общий `channelBuf`
   отдаёт все посты только первому `Collect` за прогон, второй+ `tg_botapi`-источник
   получает пусто. Подтверждено в коде (`app.go:71` — один общий `channelBuf`,
   `buffer.go` — FIFO drain), но **нигде не отражено в `POST_MVP_PLAN.md`** (там для
   этого есть готовое место — §2 "Отложенные риски").
2. **Осиротевший, но не проблема:** `docs/plans/feat-dynamic-sources.md` — намеренно
   замороженная запись (есть написанный §10 "Итог"), но на неё ничего не ссылается.
   Стоит добавить одну строку-указатель из `POST_MVP_PLAN.md:40`.

### F. Путь первого пользователя — тихие ветки

1. **`/digest` при отсутствии новых элементов молчит навсегда (главная находка).**
   `handleDigest` (`router.go:86-98`) шлёт "⏳ Собираю дайджест…" и отвечает повторно
   **только при ошибке**. `pipeline.go:66-70` при пустом `FilterUnseen` возвращает `nil`
   с логом "no new items, skipping digest" — без уведомления пользователя.
   **Подтверждено вручную** — читал `router.go:80-100` и `pipeline.go:55-80` лично: код
   действительно не шлёт финальный ответ на пустой результат. **Важный нюанс**: это не
   баг, а осознанное решение — в `pipeline.go:66` есть коммент "3. Nothing new — exit
   quietly (no empty digest)". То есть поведение сознательно закодировано, но нигде не
   объяснено пользователю (ни в README, ни в тексте `/help`).
2. **Тихие частичные отказы источников** — `pipeline.go:55-58` только логирует ошибки
   отдельных источников (`log.Warn`), что соответствует документированной "мягкой
   деградации" (критерий Этапа 5), но для *динамических* источников (`/addsource`),
   однажды прошедших валидацию и затем молча переставших работать, это нигде не
   зафиксировано как компромисс.
3. **Runtime-фолбэка LLM→offline не существует** (уточнение, не баг): `app.go:37-42`
   выбирает Client XOR Offline один раз при старте по наличию ключа. Если ключ задан и
   API падает — `pipeline.go:73-76` возвращает жёсткую ошибку, `/digest` явно покажет
   "❌ Ошибка". Отказ виден пользователю, как и задумано.

## Часть 2 — Профиль aiTelegaBot (база для сравнения)

**Что уже есть:** маршрутизация команд (`/start /help /digest /sources /addsource
/removesource`) через `go-telegram/bot`; сбор из RSS/Atom/arXiv (gofeed) и HN (ручной
`net/http`+JSON); Telegram-источники через Bot API и best-effort `t.me/s` скрейпинг;
MTProto для приватных каналов (Фаза 2, полностью реализована); дедуп по URL/GUID в
SQLite; суммаризация через ручной `net/http`-клиент с retry+backoff и детерминированным
offline-фолбэком (BYOK, ключ никогда не логируется); ежедневный планировщик на
`time.Timer`/`Ticker`, restart-safe; Docker multi-stage статический бинарник; **реально
задеплоено на прод-VPS** и живо проверено.

**Жёсткие ограничения, которые определяют applicability-вердикты ниже:**
- Соло pet-проект, не бизнес — экономическая целесообразность необязательна.
- Приоритет — учить Go/stdlib, а не тащить SDK/фреймворки.
- Дешёвый VPS, **подтверждённо ~458MB RAM** — `docker compose up --build` уже один раз
  убивал OOM-киллером сборку gotd/td прямо на сервере (обходной путь — собирать образ
  локально и `docker save`/`scp`/`docker load`).
- Только SQLite, никаких внешних БД/очередей.
- Только один пользователь, никакой multi-tenancy (v2-кандидат "по спросу", не сейчас).
- BYOK — проект никогда не хостит/проксирует чужие LLM-ключи (архитектурная граница,
  не временное упрощение MVP).
- Всё живёт под `internal/` (нет `pkg/`) — не должен случайно импортироваться как
  библиотека раньше времени.
- Постоянно вне скоупа ("Never", не просто отложено): LLM-прокси, платный SaaS с
  биллингом в боте, массовый скрейпинг чужих приватных данных, спам-рассылка.

## Часть 3 — Конкурентный ландшафт

48 уникальных продуктов (найдено 51 по имени, 3 пары оказались одним и тем же продуктом
под разными именами и объединены). Формат на продукт: что это, ключевые фичи, плюсы,
минусы, цена/лицензия, применимость к aiTelegaBot (adopt/consider/skip с обоснованием),
уверенность/источник.

### A. Telegram-first боты и сервисы дайджестов

#### Junction Bot — коммерческий SaaS
`junctionbot.io` · закрытый код, только хостинг. Мониторит публичные/закрытые Telegram-чаты
(приватные — через подключение аккаунта пользователя), дайджест по кастомному AI-промпту
с выбором модели и "креативности", гибкое расписание (несколько слотов в день), доставка
только в Telegram. Цены €3–142/мес (без бессрочного free), 7-дневный триал.
**Плюсы:** гибкая настройка промпта/расписания, доступ к приватным чатам через MTProto-подобный механизм.
**Минусы:** нет self-hosting, дедуп не документирован, разные версии прайса на сайте — низкая надёжность документации поставщика.
**Применимость:** *skip* — модель "AI-промпт вместо жёсткого пайплайна" интересна философски,
но противоречит BYOK/self-host принципам aiTelegaBot; ничего технически нового для
Go-реализации. *Consider* — идея "несколько слотов дайджеста в день" уже есть в
`POST_MVP_PLAN.md` §1.2 как "multiple schedules" независимо от этого конкурента.
Confidence: medium.

#### RSS-to-Telegram-Bot (Rongronggg9) — он же «telegram-rss-bot»
github.com/Rongronggg9/RSS-to-Telegram-Bot · open source, AGPLv3+ · ~2.1k★, ищет мейнтейнера.
Чистый relay (не LLM-суммаризатор): OPML import/export, покомандное управление подпиской
(`/sub /unsub /list /import /export`), богатое форматирование, HTTP-кэширование, мультиюзер/i18n.
**Плюсы:** зрелый, много пользователей, сильная точность рендеринга Telegram-разметки.
**Минусы:** нет AI-суммаризации вовсе — другой класс продукта; AGPL требует раскрытия форков;
проект ищет нового мейнтейнера.
**Применимость:**
- *adopt* — **OPML import/export**: расширяет уже существующий `/addsource`, массовое
  добавление/выгрузка источников. Effort: ~0.5–1 день (XML-парсинг stdlib `encoding/xml`).
- *adopt* — **HTTP conditional fetch (ETag/Last-Modified)**: снижает нагрузку на фетчер,
  идиоматично для `net/http`. Effort: ~0.5 дня.
- *skip* — мультиюзер/i18n, проксирование, forwarding медиа — прямо противоречат
  single-user дизайну и текущему скоупу.
Confidence: high (перепроверено двумя независимыми заходами, оба сошлись).

#### telegram-ai-digest (sliday)
github.com/sliday/telegram-ai-digest · open source, Apache-2.0 · 55★.
Однофайловый Python-скрипт: Telethon (MTProto user-сессия) читает несколько каналов,
Claude Haiku суммаризирует в фиксированную (иврит!) таксономию, публикует в Telegraph.
**Важно:** README устарел и не соответствует текущему коду (заявляет Replicate/FLUX,
которого нет).
**Минусы:** захардкожен под одну задачу и язык; требует полного user-аккаунта (тот же
риск, что и MTProto-фаза самого aiTelegaBot); нет планировщика/дедупа/source-management.
**Применимость:** *skip* целиком — специализирован под чужой узкий кейс, ничего
переносимого архитектурно; урок разве что "не дай README разойтись с кодом" (сам аудит
Части 1 поймал похожую проблему в этом же проекте). Confidence: high.

#### TelegramChannelsSummarizer
github.com/Undermove/TelegramChannelsSummarizer · MIT · практически заброшен (0★, коммит
2025-05). Twitter/GramJS + двухпроходная OpenAI суммаризация в фиксированные категории на
русском, запуск по GitHub Actions cron.
**Применимость:** *skip* — нет постоянного состояния, нет дедупа, GitHub Actions как
runtime противоречит цели "постоянный VPS-сервис". Единственная полезная мысль — двухпроходная
суммаризация (сначала темы, потом дайджест) уже концептуально близка к тому, что должен
делать `internal/digest` при качественной суммаризации; не отдельная фича для роадмапа.
Confidence: high.

#### telegram_link_summarizer_agent
github.com/kargarisaac/telegram_link_summarizer_agent · Apache-2.0 · 155★. On-demand
суммаризация ссылки, вставленной в чат (статьи/PDF/YouTube/Twitter/LinkedIn) через
LangGraph+BAML агент.
**Применимость:** *consider* — идея команды `/summarize <ссылка>` по запросу (не по
расписанию) — реальный, дешёвый UX-довесок к уже существующим slash-командам; можно
переиспользовать существующий LLM-клиент вместо тяжёлого LangGraph-стека. Effort: M
(нужен HTML/PDF-экстрактор на Go, например `go-readability`). *skip* — Playwright/AgentQL/
twitterapi.io для YouTube/LinkedIn/Twitter — слишком тяжёлые внешние зависимости для
458MB VPS. Confidence: medium.

#### Newsbot (MikoSNSQNN)
github.com/MikoSNSQNN/Newsbot · без лицензии (юридически "все права защищены"),
заброшен (3 коммита за один день). Один RSS-источник → одна фиксированная канал.
**Важно:** заявленная в README OpenAI-суммаризация — мёртвый код, никогда не вызывается.
**Применимость:** *skip* полностью — по всем осям строго беднее уже реализованного
aiTelegaBot (один источник vs много, нет дедупа toolgrade, нет команд управления).
Полезно как контрпример: "заявленная в README фича, которой нет в коде" — ровно тот
паттерн, который поймал docs-аудит этого же проекта. Confidence: high.

#### The Feed Reader Bot — коммерческий SaaS
thefeedreaderbot.com · закрытый код. RSS+YouTube+X+Facebook+TikTok+Instagram+email+сайты
без RSS (AI-генератор фида), мультиканальная доставка (Telegram+Discord+Slack+Signal+
WhatsApp на платных тарифах). AI-суммаризация — **только на Elite/Ultimate** (€12–19/мес),
лимит ~10k токенов/мес.
**Применимость:** *skip* — закрытая SaaS, платный AI-лимит абсурдно мал для ежедневного
дайджеста (10k токенов ~ 1-2 дайджеста). Единственная идея — "AI-генератор RSS из сайта
без фида" интересна как паттерн для будущего source-типа "readability-scrape" (уже в
POST_MVP_PLAN §1.1), но не как код для копирования (закрытый). Confidence: medium.

#### RSS Reader AI — коммерческий SaaS
rssreaderai.com · закрытый код, LLM-провайдер не раскрыт. Multi-level summaries
(one-line/bullets/deep-dive), голосовые брифинги (TTS), синхронизация web+Telegram,
оплата в Telegram Stars.
**Применимость:** *consider* — многоуровневая суммаризация (одна строка vs подробно) —
дешёвая prompt-фича, можно сделать конфигом уровня детализации в существующем LLM-промпте.
Effort: S. *skip* — TTS-голос, веб-приложение, крипто-оплата — избыточны для single-user
бота. Confidence: low (сам продукт слабо верифицируем — минимальный независимый след).

#### teledigest
github.com/igoropaniuk/teledigest · MIT · маленький (23★), Telethon-агрегация только
Telegram-каналов, OpenAI/Ollama суммаризация, Telegraph fallback для длинных постов.
**Важно:** статическая конфигурация источников (открытый issue #29 с просьбой добавить
динамику), т.е. **не** имеет уже реализованной в aiTelegaBot фичи /addsource.
**Применимость:** *adopt-idea* — Telegraph fallback для дайджестов, превышающих лимит

  именно так, а не склеивает N отдельных LLM-вызовов. Если нет — небольшая доработка
  промпта. Effort: S (проверка) / M (если нужна переработка).
- *consider* — команда админ-регенерации конкретного прошлого дайджеста (`/regenerate`)
  — дёшево на существующей инфраструктуре команд. Effort: S.
- *skip (масштаб)* — цепочка из 5 провайдеров избыточна для single-user BYOK-бота с одним
  настроенным ключом + offline-фолбэком; сама *идея* "если провайдер недоступен —
  переключиться на следующий" стоит проверить на предмет retry/backoff-надёжности в
  текущем `internal/llm`, но не разворачивать в 5-провайдерный waterfall.
Confidence: medium.

#### hn_summary (jiggy-ai)
github.com/jiggy-ai/hn_summary · Apache-2.0 · 249★, неактивен с мая 2024. Событийно-
управляемый (не батч/cron) — суммаризирует каждую новую топовую историю сразу через
GPT-3.5, публикует в один публичный broadcast-канал, PostgreSQL.
*Примечание методологии:* второй, более generic "hn_summary" кандидат из отдельного
захода поиска не удалось верифицировать как отдельный проект — обе находки, вероятно,
указывают на этот же репозиторий.
**Применимость:** *skip* — событийная (не расписанная) публикация означает спам в течение
дня для одного пользователя, что прямо противоречит формату "один сжатый дайджест в
день"; требует PostgreSQL (внешняя БД, запрещено); публичный broadcast-канал вместо
single-user. Единственный урок — реальная реализация дедупа через in-memory + Postgres
seen-set, но у aiTelegaBot уже есть более надёжный SQLite-based дедуп. Confidence: high.

#### hnbriefs (johntad110)
github.com/johntad110/hnbriefs · MIT · очень маленький (6★), README расходится с кодом
(неверный env var для LLM-ключа, неверный порог score). Опрос раз в 10 минут (не cron),
Gemini-суммаризация статьи, TTLCache-дедуп из плоского файла (не БД), одна захардкоженная
цель.
**Применимость:** *consider* — единственная реально новая идея: **настраиваемый
минимальный score-порог для HN-пунктов** как quality-фильтр — простое поле конфига,
нет архитектурного конфликта. Effort: S. Остальное — *skip*, так как aiTelegaBot уже
превосходит этот проект почти по всем осям (SQLite vs плоский файл, cron vs polling-loop,
команды управления vs захардкожено, Docker vs голый скрипт). Показательный контрпример:
собственный баг этого проекта (README не совпадает с кодом) — тот же класс проблемы,
что docs-аудит нашёл в самом aiTelegaBot (Часть 1, находка B и C) — повод быть строже
к синхронизации README/кода вперёд. Confidence: high (полная per-feature адверсариальная
проверка выполнена Workflow).

#### hackernewsbot (phil-r)
github.com/phil-r/hackernewsbot · MIT · заброшен с 2023, Google App Engine (Python 2-эра).
Пороговый фильтр по score (100+), без LLM, публикация raw title/link/score в один канал.
**Применимость:** *skip* полностью — не суммаризатор, привязан к устаревшей GCP-платформе.
Единственный урок — простой числовой score-порог стабильно работал в проде с 2016 года,
подтверждает, что "consider"-пункт по score-фильтру (см. hnbriefs выше) — не изобретение
велосипеда, а проверенный временем паттерн. Confidence: high.

#### FastDigest (built-by-as)
github.com/built-by-as/FastDigest · MIT · 14★. Chrome-расширение (не бот/сервис!) —
кнопка "Summarize" для веток комментариев HN, OpenAI или локальный Ollama.
**Применимость:** *consider* — суммаризация **веток комментариев** (не только статьи-
ссылки) — реальная неохваченная идея: "что думает HN" отдельно от "о чём статья". Effort:
M (новый вызов HN API за деревом комментариев + больше LLM-токенов на дайджест). *skip*
— доставка через browser extension полностью не соответствует Telegram-first дизайну.
Confidence: high.

#### auto-news (finaldie) — крупнейшая находка в исследовании
github.com/finaldie/auto-news · MIT (ядро) + коммерческий "Dots Agent" сверху · **905★,
110 форков** — на порядок популярнее остальных self-hosted аналогов. Мульти-источник
(Twitter/X, RSS, YouTube с авто-транскрипцией, веб-статьи, Reddit, личные заметки),
LangChain-суммаризация с выбором провайдера (OpenAI/Gemini/**Ollama**), оркестрация через
Apache Airflow, деплой Docker Compose/K8s/Helm, Notion как читалка.
**Применимость:**
- *adopt (уже частично так)* — плагируемый LLM-бэкенд (OpenAI/Gemini/Ollama через одну
  абстракцию) — тот же дух, что уже есть у aiTelegaBot (BYOK + offline фолбэк); стоит
  свериться, что `internal/llm`-клиент достаточно абстрагирован для добавления второго
  провайдера в будущем без переписывания.
- *consider (POST_MVP)* — Twitter/X и Reddit как источники — тот же тип задачи, что уже
  решённые RSS/HN-коллекторы (новый `feed`-источник), но упирается в платный/ограниченный
  доступ к API — реальный барьер, не только код. Уже упомянуто в `POST_MVP_PLAN.md`.
- *consider (POST_MVP)* — фильтрация по интересам перед суммаризацией (embedding/LLM-
  классификация) — усилило бы "important only"-пункт `POST_MVP_PLAN.md` §1.2.
- *skip категорически* — Apache Airflow (типично 2-4GB+ RAM только под оркестратор — на
  порядок больше всего VPS-бюджета aiTelegaBot), Kubernetes/Helm/ArgoCD, Notion-читалка,
  companion mobile apps — прямой конфликт с "один статический Go-бинарник на дешёвом VPS".
  Именно масштаб этого проекта (905★, коммерческий слой) — сигнал, что "богатый
  мульти-источниковый дайджест-бот" как ниша реально востребована, но инфраструктурный
  путь auto-news не подходит формату соло pet-проекта.
Confidence: high (два независимых захода, консистентные данные).

### F. Self-hosted мульти-источниковые пайплайны и RSS-инфраструктура

#### FreshRSS (базовый продукт, обнаружен через generic-запрос "news-aggregator")
github.com/FreshRSS/FreshRSS · AGPL-3.0 · ~15.9k★ — самый звёздный проект во всём
исследовании. PHP, но крайне лёгкий по ресурсам (запускается на Raspberry Pi), поддерживает

только через сторонние расширения (см. секцию B выше).
**Применимость:** *consider* — **XPath/JSON-скрейпинг как fallback для сайтов без RSS**
прямо реализует уже запланированный в `POST_MVP_PLAN.md` §1.1 пункт "readability-style
extraction для сайтов без фида". Effort: M (новый source-тип + HTML-парсинг, `golang.org/
x/net/html` или `goquery`-эквивалент). *skip* — WebSub (требует публичный вебхук-эндпойнт
на VPS — новая поверхность атаки/операционная сложность), мультиюзер/OIDC, отдельный CLI

#### Precis
github.com/leozqin/precis · MIT · 93★. Python/FastAPI, YAML-конфиг, Ollama/OpenAI
суммаризация, мультиканальные уведомления (Matrix/Slack/Jira/ntfy), **прозрачный
User-Agent** (представляется владельцам контента, не спуфит).
**Применимость:**
- *adopt* — **прозрачный User-Agent в HTTP-фетчере** — тривиально, хорошая гигиена по
  отношению к владельцам источников, один constant/заголовок в уже существующем
  `net/http`-клиенте. Effort: тривиально.
- *consider* — **команда/скрипт бэкапа SQLite** (`sqlite3 .backup` или копирование файла
  при остановленном процессе) — реально полезно перед рискованными операциями (особенно

- *skip* — мультиканальные уведомления (Matrix/Slack/Jira/ntfy) — единственная цель
  доставки уже Telegram, абстракция не нужна.
Confidence: high.

## Часть 4 — Официальные Claude Code скиллы для проекта

Перепроверено вручную через `gh api repos/anthropics/claude-plugins-official/contents/plugins`
— все три плагина подтверждены существующими в официальном маркетплейсе Anthropic
(`anthropics/claude-plugins-official`), помимо уже используемых в проекте
(`go-telegram-bot-dev`, `code-review`, `security-review`, `run`, `code-docs-audit`).

### `gopls-lsp`
Прямое структурное попадание — весь проект на Go (`cmd/bot`, `internal/*`). Подключает
реальный `gopls` language server к Claude Code: точный go-to-definition, find-references,
rename через границы пакетов вместо grep-приближений. Особенно полезно для проекта с
множеством `internal/`-пакетов и интерфейсных границ (source-интерфейсы `internal/
telegram`, коллекторы `internal/feed`).
**Установка:** нужен `gopls` в PATH (`go install golang.org/x/tools/gopls@latest`),
`/plugin marketplace add anthropics/claude-plugins-official`, затем `/plugin install
gopls-lsp@anthropic-agent-skills` (точный алиас маркетплейса уточнить через `/plugin
marketplace list`). После установки активируется автоматически на `.go`-файлах.

### `claude-md-management`
У проекта необычно детальный, нагруженный `CLAUDE.md` (git-workflow, модель-политика,
security-правила для токенов/ключей/MTProto-сессии, архитектурные решения) плюс отдельный
cross-session memory-файл (`MEMORY.md`, ссылающийся на `vps_deployment.md` и
`feat-dynamic-sources.md`). Скилл предназначен для аудита качества CLAUDE.md и фиксации
session-уроков обратно в память — отличается от `code-docs-audit` (тот проверяет
PLAN.md/TECHNICAL_PLAN.md/README против кода, не сам CLAUDE.md/memory-слой).
**Применение:** периодически (например, по своему же чекпоинт-правилу из глобального
CLAUDE.md пользователя) для аудита CLAUDE.md на устаревание.

### `hookify`
У проекта есть жёсткие, но пока чисто текстовые инварианты в CLAUDE.md: никогда не
коммитить `*.session`/`.env`/`*.db`, никогда не логировать `LLM_API_KEY`/токен бота,
MTProto-сессия — `0600` вне git. Прозаические правила в CLAUDE.md — advisory, не
принудительны. `hookify` превращает такие правила в реальные PreToolUse/Stop-хуки (напр.
блокировка `git add`/`commit`, затрагивающего `*.session`/`.env`; предупреждение о
логировании переменных, похожих на ключ) на простом markdown-описании. В репозитории
сейчас нет `.claude/settings.json`-хуков — это будет новое принудительное соблюдение, не
дублирование.
**Применение:** `/plugin install hookify@anthropic-agent-skills`, затем описать правило
простым текстом ("никогда не давай коммиту содержать `.session`, `.session-journal` или
`.env`-файл" / "предупреди, если `log`/`slog`-вызов включает переменную с именем token,
apiKey, key").

## Часть 5 — Синтез и рекомендации

### Что подтвердилось как правильный выбор (ничего менять не нужно)
- **Go + статический бинарник + SQLite** — Miniflux (~15.9k★ экосистема FreshRSS) и сам
  факт, что даже амбициозные self-hosted конкуренты (auto-news, 905★) утыкаются в тяжёлую
  инфраструктуру (Airflow, K8s) там, где Go-подход остаётся лёгким — прямое архитектурное
  подтверждение.
- **BYOK без прокси чужих ключей** — экономика конкурентов с "AI-кредитами" (RSS.app: 5
  кредитов/мес на платном тарифе) наглядно показывает цену отказа от BYOK: искусственный
  дефицит там, где у пользователя с собственным ключом его просто нет.
- **Мульти-источниковость "из коробки" (RSS+arXiv+HN+Telegram)** — большинство найденных
  конкурентов специализированы на одном источнике (arXiv-only, HN-only, Telegram-only);
  сравнимого по охвату single-user self-hosted инструмента на Go не найдено.

### Конкретные "adopt"-кандидаты (низкий эффорт, реальная польза, без архитектурного конфликта)
| Идея | Источник | Effort | Куда |
|---|---|---|---|
| OPML import/export для источников | RSS-to-Telegram-Bot | S | расширение `/addsource` |
| HTTP conditional fetch (ETag/Last-Modified) | RSS-to-Telegram-Bot | S | фетчер источников |
| Regex/логический фильтр контента (AND/OR/NOT) | RSSbrew | S–M | pipeline перед дедупом |
| Per-feed User-Agent override | RSSbrew, Precis | тривиально | HTTP-клиент фетчера |
| Прозрачный User-Agent (не спуфить) | Precis | тривиально | HTTP-клиент фетчера |
| SQLite backup-команда | Precis | S | операционная гигиена |
| Строгий лимит длины дайджеста/пункта в промпте | TLDR Newsletter | тривиально | LLM-промпт |
| Telegraph fallback для дайджестов >4096 симв. | teledigest | S–M | доставка |
| Настраиваемый минимальный score-порог для HN | hnbriefs, hackernewsbot | S | HN-коллектор |

### Кандидаты в POST_MVP (осмысленные, но требуют реального планирования)
- XPath/readability-скрейпинг для сайтов без RSS (FreshRSS, Newsletter & Blog Digester) —
  уже есть строкой в `POST_MVP_PLAN.md` §1.1, это исследование подтверждает спрос на неё.
- Суммаризация полного текста статьи по ссылке, а не только сниппета (hacker-news-digest) —
  реально повышает качество дайджеста, но требует readability-парсера и CPU-бюджета.
- Суммаризация веток комментариев HN отдельно от статьи (FastDigest) — новый угол на уже
  собираемый источник.
- On-demand `/summarize <ссылка>` команда (telegram_link_summarizer_agent) — использует уже
  существующий LLM-клиент, не требует нового источника.
- "Digest mode" — единый связный LLM-проход по всем пунктам дня вместо N независимых
  сводок (hn-brief) — стоит сверить с текущей реализацией `internal/digest`, возможно уже
  так и есть.

### Явно skip (архитектурный конфликт с зафиксированными ограничениями)
Apache Airflow / Kubernetes / Helm (RAM), внешние БД типа Postgres (SQLite-only принцип),
serverless/Cloudflare Workers как runtime (цель — постоянный VPS-сервис), мультиюзер/i18n
(single-user принцип), веб-админка (Telegram-command-driven UX), сторонние платные
API-цепочки для соцсетей (X/LinkedIn/TikTok — вне текущего скоупа источников), LLM-прокси
или продажа доступа другим пользователям (прямой запрет в CLAUDE.md).

### Рекомендация по приоритету
Из "adopt"-таблицы выше — **regex-фильтр контента** и **строгий лимит длины дайджеста**
дают наибольшее соотношение пользы к усилиям и закрывают реальные, а не гипотетические
пробелы (фильтрация контента у aiTelegaBot сейчас отсутствует вовсе — есть только дедуп).
Остальное — по вкусу и по факту жалоб на текущее поведение бота в реальном использовании.
