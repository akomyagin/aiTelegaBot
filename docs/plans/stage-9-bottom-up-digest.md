Ветка: `stage-9/bottom-up-digest` (PR в `master`). Исполнитель: Agent `model: "opus"`.
Конвенции кода: `.claude/skills/go-telegram-bot-dev/SKILL.md` (обязателен к прочтению

## 1. Цель

Перестроить дайджест «снизу вверх» — от сообщения к общему выпуску (спецификация
пользователя 2026-10-21; его решения зафиксированы в §4.0 и не переоткрываются):

1. **Классификация каждого сообщения**: новость, статья, обучающий материал,
   курс, высказывание/мнение, медиа-пост, реклама, прочее. Реклама выбрасывается
   полностью; курс попадает в дайджест одной фразой («курс + тема») без перехода
   и саммари; остальные классы — полный цикл.
2. **Внешние ссылки**: собирать контент по ссылкам (кроме рекламы), саммари на
   каждую статью («список статей» — по каждой); кеш ссылок — одна статья из двух
   каналов не саммаризится дважды.
3. **Семантический дедуп**: переписанные дубли (особенно новости) из разных
   источников схлопываются в один первоисточник; дубли не показываются.
4. **Четырёхуровневая навигация** (иерархия пользователя: общий дайджест → тема →
   топик → сообщение; «тема» = topics Этапа 8, «топик» = источник/канал в теме):
   - **L0** общий дайджест: общее саммари + список тем;
   - **L1** тема: общее саммари темы + топики **человекочитаемыми названиями** —
     списком в тексте и inline-кнопками с полными именами (одна на строку);
   - **L2** топик: общее саммари топика + сообщения с саммари каждого, под
     каждым — ссылка «перейти» (единственная точка выхода из бота);
   - **L3** сообщение: ПОЛНЫЙ текст + медиа + «перейти в источник».
5. **Медиа**: если картинка — основное содержание поста, показать её в боте
   (превью и полный вид, без перехода в канал); ссылку/file_id хранить.
6. **Идемпотентность обработки**: упавший прогон не теряет работу — класс,
   саммари, кластер дублей и кеш ссылок переживают рестарт (SQLite), следующий
   прогон не переспрашивает LLM о том же.

Эволюционируем существующий pipeline (`internal/digest/pipeline.go`, 9 шагов),
рендеры (`render.go`, `drilldown.go`) и схему v4 — не сносим.

## 2. Ограничения и границы (что НЕ делаем)

- **VPS ~458 MB RAM** (memory `vps_deployment.md`): никакого headless-браузера,
  никаких локальных моделей, никакая тяжёлая обработка изображений. Извлечение
  текста из HTML — `golang.org/x/net/html` (уже зависимость). LLM — только
  внешний OpenAI-совместимый chat-completions endpoint (`internal/llm/client.go`).
- **Embeddings НЕ гарантированы** (BYOK, один chat-endpoint) — дедуп только
  батч-LLM по заголовкам/лидам, не векторами.
- **Видео не показываем в боте** (решение планировщика по стоимости/RAM/трафику):
  видео-посты классифицируются как media, в L3 — текст + «перейти в источник».
  Триггер пересмотра: пользователь попросит видео (§7).
- **Реклама-фильтр не идеален**: best-effort классификация LLM + кеш; пропуск
  рекламы принимается, жалобная кнопка «это реклама» — вне этапа.
- **«Показать дубли» — вне этапа**: кластеры хранятся в БД, UI-просмотр дублей
  не делаем (триггер §7).
- **Кросс-прогонный семантический дедуп — вне этапа**: кластеризация только
  внутри темы одного прогона (вчерашняя новость, пересказанная сегодня, не
  схлопывается). Точный дедуп по `seen_items` сохраняется. Триггер §7.
- **robots.txt не парсим** (решение планировщика): single-user, ≤1 GET на URL,
  кеш навсегда, вежливый User-Agent, 429/503 — не ретраим. Этика: не качаем
  платный контент обходными путями, не следуем редиректам дольше 3 хоппов.
- **Не трогаем**: scheduler (слот + meta `last_digest_date`), MTProto-логин и
  шифрование сессии, транспорт LLM-клиента (retry/backoff — только новые методы
  поверх), Dockerfile/compose, команды управления источниками/темами Этапа 8.
- **Альбомы/медиа-группы не склеиваем**: берём первое фото поста (решение
  планировщика); триггер §7.
- `pkg/` не появляется; новый код — в `internal/*` (SKILL.md §1).
- **Старые доставленные сообщения не ломаются**: legacy-колбеки `L2:`/`L3:`
  продолжают работать (§4.6), legacy-строки `digest_items` (без full_text/class)
  рендерятся деградированно, но без ошибок.

## 3. Критерий готовности всего этапа

- В прогоне каждое сообщение классифицировано; реклама и не-первоисточники не
  попадают в дайджест и не показываются; курс — одна строка «🎓 Курс: …» без
  кнопки полного текста; повторный прогон после краха НЕ делает повторных
  LLM-вызовов по уже обработанным сообщениям (проверяется счётчиком фейка).
- Статья по внешней ссылке саммаризируется; «список статей» — саммари по
  каждой; одна и та же URL из двух каналов саммаризится один раз (link_cache).
- L0→L1→L2→L3 работают через edit одного сообщения и переживают рестарт бота
  (данные в SQLite); L1 показывает топики полными человекочитаемыми именами
  (текст + кнопки); L3 — полный текст сообщения + «перейти в источник»
  (единственная внешняя ссылка уровня).
- Пост с картинкой (tg_botapi / tg_public / rss / tg_mtproto) — в L3 кнопка
  «🖼 Фото» показывает фото в боте (sendPhoto отдельным сообщением, превью +
  полный вид по тапу), «✖ Закрыть» удаляет его; file_id/URL сохранены в БД и
  переживают рестарт.
- Offline-режим (без LLM_API_KEY): каждый уровень деградирует детерминированно
  (§4.9), прогон не падает.
- Все динамические тексты через `EscapeHTML`; все новые колбеки ≤64 байт;
  owner-чек на всех новых ветках; секреты не логируются.
- `go build ./... && go vet ./... && gofmt -l . (пусто) && go test -race ./...`
  зелёные; golden обновлены осознанно; ручной сценарий с реальным токеном —
  на деплое (как в Этапе 8, в среде агентов токена нет).

## 4. Ключевые архитектурные решения (приняты, не переоткрывать без нужды)

### 4.0. Решения пользователя (зафиксированы 2026-10-21)

1. Иерархия: **общий дайджест → тема → топик → сообщение**. «Тема» = topics из
   /topics (Этап 8). «Топик» = **источник/канал** в рамках темы (не LLM-кластер).
   Дубли-пересказы из разных источников схлопываются в один первоисточник.
2. Навигация в виде «тема»: топики — inline-кнопки с ПОЛНЫМИ названиями (одна на
   строку) + тот же список именами в тексте сообщения; текстовые ссылки в теле —
   только внешние URL (ограничение Telegram ParseMode).
3. LLM-бюджет: пользователь согласен на любой режим — дефолт выбран
   обоснованно (§4.8), альтернативы и триггеры переключения зафиксированы там же.

### 4.1. Таксономия классификации и что делаем с каждым классом

Классы (`internal/llm/classify.go`, строковые константы — в БД и JSON):

| Класс | Значение | Обработка |
|---|---|---|
| `news` | новость | полный цикл: саммари, ссылки, дедуп-приоритет |
| `article` | статья / лонгрид | полный цикл |
| `tutorial` | обучающий материал (не курс) | полный цикл |
| `course` | обучающий КУРС | одна фраза «курс + тема»; ссылки НЕ fetch'им; саммари не просим; в L2 строка «🎓 Курс: …» + «перейти»; кнопки «Читать полностью» нет |
| `opinion` | высказывание/мнение по теме | полный цикл |
| `media` | медиа-пост (картинка/видео — основное содержание) | полный цикл + показ медиа (§4.5) |
| `ad` | реклама | ВЫБРАСЫВАЕМ полностью: не в дайджесте, сразу seen (§4.2), status=`dropped_ad` |
| `other` | прочее | полный цикл (без спецобработки) |

Где классификация происходит: **при run, не при collect** (решение
планировщика). Collect — механический сбор из источников без LLM (источники
переиспользуются между прогонами, buffer tg_botapi дренируется один раз); вся
LLM-обработка живёт в pipeline и кэшируется в `message_state` по `dedup_key`.
Идемпотентность: перед LLM pipeline читает `message_state` — сохранённые
class/summary/кластер/медиа НЕ пересчитываются между прогонами и рестартами;
LLM-сбой оставляет status=`failed` и элемент НЕ seen (подберёт следующий прогон,
семантика §4.9 Этапа 8).

Offline (без LLM_API_KEY): детерминированная деградация — все элементы
class=`other` (реклама НЕ фильтруется — осознанно: ложное срабатывание
эвристики хуже пропуска), саммари = `extractLead` (существующий), дедуп =
точное совпадение нормализованного заголовка (lowercase, без пунктуации по
краям). Никаких вызовов сети.

### 4.2. Схема БД — миграция v5 (append в `internal/storage/migrate.go`, v1–v4 не правим)

```sql
-- v5 (Этап 9): состояние обработки сообщений, кеш ссылок и их привязка к
-- сообщениям, общее саммари прогона, полный текст/класс/медиа у digest_items.
-- message_state — кеш обработки: упавший прогон не теряет LLM-работу, а
-- следующий не переспрашивает LLM о том же (ключ = dedup_key, тот же, что в
-- seen_items — «эволюция»: seen_items остаётся таблицей ДОСТАВКИ (что уже было
-- показано), message_state — таблицей ОБРАБОТКИ (что уже классифицировано/
-- саммаризовано). digest_items остаётся per-run снапшотом для навигации.)
CREATE TABLE IF NOT EXISTS message_state (
    dedup_key  TEXT PRIMARY KEY,
    source_id  INTEGER,
    topic_id   INTEGER,
    class      TEXT NOT NULL DEFAULT '',        -- §4.1; '' = не классифицировано
    cluster_id TEXT NOT NULL DEFAULT '',        -- '<runID>:<n>'; '' = не в кластере
    is_primary INTEGER NOT NULL DEFAULT 1,      -- 0 = дубль, не показывается
    summary    TEXT NOT NULL DEFAULT '',        -- саммари сообщения (1–2 предложения)
    media_kind TEXT NOT NULL DEFAULT '',        -- '' | 'photo'
    media_ref  TEXT NOT NULL DEFAULT '',        -- tg file_id ИЛИ http(s) URL картинки
    status     TEXT NOT NULL DEFAULT 'new',     -- new|done|dropped_ad|dropped_dup|failed
    updated_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS link_cache (
    url        TEXT PRIMARY KEY,
    kind       TEXT NOT NULL DEFAULT '',        -- article|course|ad|other|unavailable
    title      TEXT NOT NULL DEFAULT '',
    summary    TEXT NOT NULL DEFAULT '',
    fetched_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS item_links (
    dedup_key TEXT NOT NULL,
    url       TEXT NOT NULL,
    kind      TEXT NOT NULL DEFAULT '',         -- класс ссылки (§4.3)
    ord       INTEGER NOT NULL DEFAULT 0,       -- порядок в сообщении
    PRIMARY KEY (dedup_key, url)
);
CREATE TABLE IF NOT EXISTS runs (
    run_id     INTEGER PRIMARY KEY,             -- Unix-секунды, как digests.run_id
    summary    TEXT NOT NULL DEFAULT '',        -- общее саммари выпуска (L0)
    created_at TEXT NOT NULL
);
ALTER TABLE digest_items ADD COLUMN full_text TEXT NOT NULL DEFAULT '';  -- до 8000 рун
ALTER TABLE digest_items ADD COLUMN class     TEXT NOT NULL DEFAULT '';
ALTER TABLE digest_items ADD COLUMN media_kind TEXT NOT NULL DEFAULT '';
ALTER TABLE digest_items ADD COLUMN media_ref  TEXT NOT NULL DEFAULT '';
```

Соотношение с существующими таблицами — **эволюция, не замена**: `seen_items`,
`digests`, `digest_items` остаются и сохраняют семантику Этапа 8 (доставка
гейтит персистенцию: `MarkDelivered` одной транзакцией). Новые колонки
`digest_items` имеют DEFAULT '' — legacy-строки читаются как «нет полного
текста/класса/медиа» и рендерятся деградированно (snippet вместо full_text).
Реклама и дубли получают seen **сразу при классификации** (до доставки,
отдельный `MarkSeenBatch`) — они никогда не показываются, терять их при сбое
доставки нечего; остальные элементы — seen только в `MarkDelivered`, как сейчас.

### 4.3. Внешние ссылки: fetcher, извлечение текста, классификация ДО fetch, кеш

Новый пакет `internal/linkfetch` (решение планировщика: не в `feed` — feed
про источники, linkfetch про контент по URL сообщения; вторая реализация
интерфейса не нужна, поэтому без интерфейса — конкретный `*Fetcher`, в
pipeline инжектится как поле):

```go
// internal/linkfetch/fetch.go
type Page struct {
    URL   string // финальный URL (после ≤3 редиректов)
    Title string // <title> или первый <h1>; может быть ""
    Text  string // извлечённый текст, ≤ fetchTextRunes (6000 рун)
}
type Fetcher struct { /* http.Client, maxBytes, userAgent */ }
func NewFetcher(hc *http.Client, maxBytes int64) *Fetcher
func (f *Fetcher) Fetch(ctx context.Context, url string) (Page, error)
```

- Таймаут 15с на URL (`LINK_FETCH_TIMEOUT`), лимит тела 2 MB
  (`LINK_FETCH_MAX_BYTES`, `io.LimitReader`), только `Content-Type: text/html`
  (и пустой) — прочее → kind=`unavailable` в кеше, не ретраим.
- Извлечение текста БЕЗ headless-браузера: `html.Parse` → обход, пропускаем
  `script/style/noscript/svg/header/footer/nav/aside/form`, конкатенируем текст
  блоков (паттерн `collectText` из `telegram/public_source.go`, но с фильтрами);
  ≤6000 рун.
- User-Agent: `Mozilla/5.0 (compatible; aiTelegaBot/1.0)` (как public_source).
  429/503/4xx/5xx → `unavailable` в кеш с `fetched_at` (не ретраим — этика/нагрузка).
- **Классификация ссылок ДО fetch** (экономия): LLM-вызов «виды ссылок» (§4.8,
  вызов E) получает текст сообщения + список URL и возвращает kind на каждую:
  `article|course|ad|other`. Fetch'им только `article` и `other` (other — как
  потенциальная статья; решение планировщика: неизвестное считаем статьёй,
  реклама и курсы отсеяны ДО скачивания). `course`/`ad` → строка в link_cache
  без fetch (kind сохраняется, summary пуст).
- «Список статей» в одном сообщении: каждая `article`-ссылка саммаризируется
  отдельно (вызов F батчем по теме, §4.8); саммари ссылок хранятся в
  `link_cache.summary` и показываются в L3-вью сообщения блоком «Ссылки:».
- **Кеш**: `link_cache` по URL — та же статья из второго канала берётся из
  кеша (без fetch и без LLM). Кеш бессрочный (single-user, объёмы малы;
  триггер §7: БД > 200 МБ → retention).
- Лимиты: ≤5 ссылок на сообщение (`LINK_PER_MESSAGE_MAX`), ≤30 fetch'ей на
  прогон (`LINK_FETCH_TOTAL_MAX`) — сверх лимита ссылки остаются в item_links
  с kind из вызова E, но без саммари (деградация, не ошибка).
- Извлечение URL из текста: детерминированный regex
  `https?://[^\s<>"']+` по `Item.URL` + `Item.Text`, дедуп по нормализованному
  URL (lowercase host, без trailing `/`, без fragment), порядок появления.
  t.me-ссылки НЕ считаем внешними (это ссылки на сами каналы — «перейти»).

### 4.4. Семантический дедуп: батч-LLM на тему, первоисточник, судьба дублей

Механизм (без embeddings — §2): **один LLM-вызов на тему** (вызов B, §4.8) —
пронумерованный список (заголовок + лид ≤200 рун + имя источника + дата), ответ
строго JSON `{"clusters":[{"indices":[1,4,7],"primary":4}]}`. В промпте
критерий первоисточника: **самая ранняя публикация; при равенстве — самый
полный текст; при равенстве — источник с меньшим source_id** (детерминированный
тай-брейк, чтобы два прогона не давали разных первоисточников). Валидация
ответа (паттерн `parseTopicSummary`): индексы вне 1..n и пересечения между
кластерами отбрасываются (первый выигрыш); `primary` ∉ indices → primary =
первый индекс кластера; одиночные элементы кластеризации не требуют.

Реклама в кластеризацию не участвует (уже выброшена). Если LLM выбрал primary,
который затем классифицирован как ad (вызовы A и B независимы) — primary
переназначается детерминированно по тому же критерию среди оставшихся.

Судьба дублей: не-первоисточники получают `message_state.status='dropped_dup'`,
`cluster_id='<runID>:<n>'`, `is_primary=0`, **сразу seen** (§4.2), в дайджест не
попадают. Строки хранятся — будущее «показать дубли» (§2 — вне этапа) прочитает
кластер без пересчёта. Подсчёт дублей в UI не показываем (решение
планировщика: чистый вид; триггер §7).

Кросс-прогон: только `seen_items` (точный дедуп). Триггеры пересмотра (§7):
стоимость вызова B (он дешевле вызова A — только заголовки) и качество (жалобы
на нераспознанные дубли → поднять лид до 400 рун / включить опубликованные
даты в сравнение).

### 4.5. Медиа: откуда картинка у каждого kind источника, хранение, показ в боте

`feed.Item` получает три аддитивных поля (DedupKey не меняется):

```go
MediaKind   string // "" | "photo" (видео не несём — §2)
MediaFileID string // tg_botapi: file_id фото из ChannelPost (бот может sendPhoto)
MediaURL    string // http(s) URL картинки (tg_public, rss)
```

По kind источника:

| Kind | Источник картинки | Что несёт Item |
|---|---|---|
| `tg_botapi` | `u.ChannelPost.Photo []PhotoSize` — СЕЙЧАС ИГНОРИРУЕТСЯ (router.go берёт только post.Text): брать FileID largest-size (последний элемент Photo); Album группируется по MediaGroupID — берём первое фото группы | MediaKind="photo", MediaFileID |
| `tg_public` | скрапинг t.me/s: `div.tgme_widget_message_photo_wrap` со `style="background-image:url('...')"` — парсим URL из style (одна regex по значению атрибута) | MediaKind="photo", MediaURL |

#### 4.5.1. MTProto: download → re-upload ботом → file_id (FloodWait! RAM!)

Фото приватного канала нельзя показать ни по URL, ни чужим file_id. Resolver в
прогоне (подэтап 9E): для tg_mtproto-элементов с MediaKind="photo" и пустым
media_ref, при промахе кеша message_state:

1. `mtproto.Client.DownloadPhoto(ctx, ref string, msgID int, destPath string) error`
   — `messages.downloadMedia`, **стриминг на диск** (temp-файл в `os.TempDir()`,
   никогда не целиком в память — RAM 458 MB), FloodWait-дисциплина как в
   GetHistory (существующие middleware+backoff).
2. Бот шлёт фото СЕБЕ в owner-чат (`SendPhoto` c `models.InputFileUpload`) → из
   ответа берёт `Photo` largest-size `FileID` → **сразу `DeleteMessage`** того
   служебного сообщения (пользователь видит только финальный дайджест).
3. file_id сохраняется в message_state/digest_items; temp-файл удаляется.

Лимит: `MT_MEDIA_REUPLOAD_MAX` (default **3** на прогон) — сверх лимита медиа
не показываем (degradation: «🖼 фото доступно в источнике»). Ошибка любого
шага → log.Warn, элемент без медиа, прогон не падает. Обоснование лимита:
каждый re-upload = download (FloodWait-риск вторичного аккаунта) + 2 Bot API
вызова; 3/день достаточно для solo-пет-проекта.

#### 4.5.2. Показ в боте: отдельное медиа-сообщение (НЕ edit текстового)

Текстовое сообщение нельзя edit'ом превратить в фото (Bot API), поэтому:
**кнопка «🖼 Фото» (`P:<digestItemID>`) в L3-вью шлёт ОТДЕЛЬНОЕ сообщение
`sendPhoto`** — photo = file_id (приоритет) или URL; caption (≤1024 байт Bot
API — режем `TruncateButtonLabelTo`-паттерном по байтам) = заголовок/саммари +
«↗ источник» текстовой ссылкой; клавиатура — одна кнопка «✖ Закрыть»
(`PDEL` — 4 байта). Telegram сам рисует превью в ленте, тап даёт полный вид —
«превью и полный вид без перехода в канал» выполнено. «✖ Закрыть» →
`deleteMessage` того же сообщения (message_id из CallbackQuery, аргументов не
нужно) + пустой ack. Обоснование отдельного сообщения против album: album
(sendMediaGroup) не даёт «закрыть» одним edit'ом и ломает «одно сообщение =
один view»-модель drill-down; отдельное фото-сообщение удаляется начисто.

sendPhoto c URL: фото качают серверы Telegram (лимит Bot API 5 MB на URL);
ошибка → ack «Не удалось показать фото» (элемент остаётся, деградация).

### 4.6. Четырёхуровневая навигация: маппинг на существующий drill-down

Уровни пользователя → view и callback_data (бюджет §4.4 Этапа 8 соблюдён):

| Уровень | View | Callback | Байт (worst) |
|---|---|---|---|
| L0 общий дайджест | доставленное сообщение прогона: общее саммари + темы (кнопки) | `T:<digestID>` у кнопок тем | 2+19=21 |
| L1 тема | саммари темы + топики именами (текст) + кнопки-имена | `S:<digestID>:<sourceID>` | 2+19+1+19=41 |
| L2 топик | саммари топика + сообщения с саммари + «перейти» под каждым + кнопки «Читать ▸» | `M:<digestItemID>` | 2+19=21 |
| L3 сообщение | полный текст + «🖼 Фото» (при медиа) + «↗ Перейти в источник» (URL-кнопка) + «◀ Назад» | `P:<digestItemID>` (фото), `S:<did>:<sid>` (назад) | 21 / 41 |
| (фото) | отдельное sendPhoto-сообщение | `PDEL` (закрыть) | 4 |
| назад L1→L0 | — | `TOC:<runID>` (существующий) | 23 |

- **Реюз префиксов (решение планировщика)**: `T:`/`TOC:` сохраняются. Вводятся
  `S:` (топик), `M:` (сообщение), `P:` (фото), `PDEL`. Legacy-префиксы остаются
  в диспетчере как alias'ы, чтобы кнопки СТАРЫХ доставленных сообщений
  работали: `L1:<did>` → как `T:<did>` (уже так); `L2:<did>` → `T:<did>`
  (ближайший новый аналог «по источникам»); `L3:<did>:<sid>` → `S:<did>:<sid>`;
  `L3:<did>:0` → `S:<did>:0` (все топики одним списком с подзаголовками —
  сохраняем существующую семантику «общий список»). Старые рендеры
  `renderDrillL2/renderDrillL3` заменяются новыми (alias'ы ведут в новые view) —
  дубль рендеров не держим.
- «Перейти» / «перейти в источник» — **внешняя URL-кнопка** (`InlineButton` c
  URL — расширение: `telegram.InlineButton` получает поле `URL string`;
  Data/URL взаимоисключающи, `inlineKeyboard` маппит URL →
  `models.InlineKeyboardButton.URL`) либо текстовая `<a href>` (в L2-строках —
  решение пользователя 2: текстовые ссылки только внешние). URL — только
  http/https, проверка схемы перед вставкой (§4.8 Этапа 8, паттерн `l3Link`).
  Для tg-источников без внешнего URL — `telegram.DeepLink(tg_peer, tg_msg_id)`.
  Это единственная точка выхода из бота.
- **L1 — топики полными именами**: текст сообщения = «• <b>имя топика</b> — N
  сообщений: саммари топика» по каждому + кнопки `{Text: имя (режется до 64
  БАЙТ — жёсткий лимит Bot API, полный имя остаётся в тексте), Data:
  "S:<did>:<sid>"}` по одной в ряд. Имя топика = отображаемое имя источника
  (решение планировщика: для tg_* — username/Title из mtproto_peers при
  наличии, иначе Ref; для rss — имя фида из sources-снапшота — расширяем
  `NewDrillDown` снапшотом `[]storage.Source` → имя = Ref, как в Этапе 8, но с
  fallback на peer-Title).
- **Куда встают существующие рендеры**: `RenderTOC` эволюционирует (добавляется
  блок общего саммари — параметр `overall string; ""` → блок отсутствует,
  legacy-восстановление без runs-строки работает); `RenderTopicBody`/
  `RenderTopicL1` ЗАМЕНЯЮТСЯ новыми `RenderTopicView` (L1) — сигнатуры меняются,
  поэтому C/D-контракт «RenderTopicL1 заморожен» явно снимается этим планом
  (этап 9 — владелец рендеров); `NewDrillDown` расширяется до диспетчера
  S:/M:/P:/PDEL + legacy-alias'ов.
- M:-view: `GetDigestItem(ctx, itemID)` (новый store-метод) → full_text (пуст →
  snippet + пометка «(сохранён только фрагмент — legacy)»), режем до 4096 рун
  guard'ом `fitDrillDownList` с «…полный текст — в источнике»; блок «Ссылки:»
  из `item_links`+`link_cache` (каждая: `<a href>kind-иконка title/домен</a> —
  summary`); кнопки: «🖼 Фото» (только при media_ref), «↗ Перейти в источник»
  (URL), «◀ Назад» → `S:<did>:<sid>` (did/sid — из самой строки digest_items).
- Крайние случаи: `S:` у digest без items (crash delivered=0, кейс Этапа 8) →
  текст «Материалов нет» + «◀ Назад»; `M:` на несуществующий id → ошибка seam'а
  (ack «Не получилось открыть», не паника — паттерн D); >4096 рун в L1/L2 —
  существующий guard «…и ещё K» (блоками: L1 — топики, L2 — сообщения).

### 4.7. Агрегация саммари: сообщение → топик → тема → выпуск; offline-деградация

Каждый уровень строится из саммари нижнего, НЕ из сырых текстов (экономия
токенов):

- **сообщение**: саммари из вызова A (§4.8) по тексту сообщения + (для статей)
  по fetched-текстам ссылок; для course — одна фраза из того же вызова.
- **топик (источник)**: вызов C — вход: саммари сообщений топика (по 1 строке);
  выход: саммари топика 1–2 предложения.
- **тема**: тот же вызов C — headline темы 2–3 предложения из саммари топиков.
- **выпуск (L0)**: вызов D (один на прогон) — общее саммари 3–5 предложений из
  headline'ов тем; хранится в `runs.summary`, показывается в RenderTOC и при
  восстановлении `TOC:<runID>`.

Offline-режим (детерминированно, без сети; все интерфейсы §4.8 реализует и
`*llm.Client`, и `*llm.Offline` — правило SKILL.md «интерфейс на второй
реализации» соблюдено):

| Уровень | Offline-деградация |
|---|---|
| класс | все `other` (без ad-фильтра) |
| саммари сообщения | `extractLead(Text)`, пустой Text → Title |
| ссылки | не fetch'им, item_links с kind=`other` без саммари |
| дедуп | точное совпадение нормализованного заголовка в теме |
| топик/тема | первые ≤3 строки «- <саммари сообщения>» (паттерн Offline.SummarizeTopic) |
| выпуск | список «- <имя темы>: N материалов» (без саммари) |

### 4.8. LLM-бюджет: дефолт (выбран), альтернативы, триггеры переключения

**Дефолт (решение планировщика в рамках решения пользователя 3): батчинг на
тему + кеш.** Инвентарь вызовов на прогон (T = число непустых тем, M = число
сообщений, L = число сообщений со ссылками):

| Вызов | Гранулярность | Вход | Выход (строго JSON, fence-strip, 1 повтор при мусоре — паттерн SummarizeTopic) |
|---|---|---|---|
| A классификация+саммари | 1 на тему | номер+title+text≤200 рун на сообщение | `{"items":[{"index":1,"class":"news","summary":"…"}]}` |
| B кластеры дублей | 1 на тему | номер+title+лид≤200+источник+дата | `{"clusters":[{"indices":[…],"primary":n}]}` |
| C агрегация | 1 на тему | саммари сообщений, сгруппированные по топикам | `{"headline":"…","sections":[{"source_index":1,"summary":"…"}]}` |
| D общее саммари | 1 на прогон | headline'ы тем | `{"summary":"…"}` |
| E виды ссылок | 1 на тему (только при L>0) | тексты сообщений + их URL | `{"links":[{"msg":1,"link":2,"kind":"article"}]}` |
| F саммари статей | 1 на тему (после fetch) | fetched-тексты ≤1500 рун на ссылку | `{"items":[{"index":1,"summary":"…"}]}` |

Итого ≈ 4T + 2T(при ссылках) + 1. Оценка на типичный день (§4.8.1): 6 тем,
120 сообщений, 30 со ссылками → ~25–30 вызовов, последовательно 3–6с каждый →
**2–4 мин** + fetch ≤30 URL × ≤2с ≈ 1 мин → прогон ≤5–6 мин.
Стоимость (gpt-4o-mini-класс): вход ~250 рун/сообщение × 120 ≈ 100–150K токенов
входа на прогон — центы в день. Все вызовы последовательные (single-user, нет
нужды в параллелизме; retry+backoff существующий).

Альтернативы (зафиксированы, переключаются по триггерам, не заранее):

1. **Экономный**: A+C слиты в один вызов на тему (классификация+саммари+
   headline+секции разом) → ~2T+1 вызовов. Триггер: прогон >10 мин ИЛИ цена
   >$1/нед. Риск: длинный JSON чаще ломается (больше фолбэков).
2. **Качественный**: саммари сообщения отдельным вызовом (не батчем) + дедуп по
   полным текстам. Триггер: жалобы на качество батч-саммари. Цена: ×M вызовов —
   практически исключено при single-VPS.
3. **Параллельный**: темы обрабатываются 2 воркерами. Триггер: прогон >10 мин
   при том, что экономный режим не помог (сначала урезка, потом параллелизм —
   порядок фиксирован).

Триггер пересмотра формата (наследуется из §7 Этапа 8): >30% фолбэков парсинга
в логах за неделю → уход от JSON к «строка на элемент» с префиксами классов.

Fallback-поведение вызова A при двойном мусоре (паттерн SummarizeTopic): все
элементы темы получают class=`other`, summary=`extractLead` — тема не
пропускается (в отличие от Этапа 8, где падал весь SummarizeTopic); status в
message_state=`done` НЕ пишется (следующий прогон переспросит LLM). Ошибка
транспорта вызова A → тема пропускается ЦЕЛИКОМ, элементы не seen (§4.9).

#### 4.8.1. Модель прогона (новый Run, шаги; §4.9 Этапа 8 сохранена)

1. SourceProvider → taggedSource → `feed.Collect` (без изменений).
2. `FilterUnseen` → fresh; пусто → log + nil (без изменений).
3. `GetMessageStates(keys)` — вычитываем кеш; group by topic (без изменений).
4. На каждую тему (последовательно):
   a. неклассифицированные → вызов A (+B кластеры) → `UpsertMessageState`
      (class/summary/cluster — КАЖДЫЙ элемент сразу, крах не теряет работу);
   b. ad → status=`dropped_ad` + `MarkSeenBatch`; dup (is_primary=0) →
      `dropped_dup` + seen; course → summary одна фраза;
   c. ссылки primary-элементов (кроме course/ad): вызов E → item_links;
      fetch article/other (кеш link_cache) → вызов F → link_cache.summary;
   d. вызов C (headline темы + саммари топиков);
   e. `RenderTopicView` → `InsertDigest(delivered=0)`; digest_items теперь
      только primary-не-ad элементы, с full_text/class/media из
      message_state+Item.
5. Все темы упали → ошибка Run (без изменений).
6. вызов D (общее саммари) → `UpsertRunSummary(runID, summary)`; сбой D —
   log-only, L0 без общего саммари (деградация, не ошибка).
7. `RenderTOC(entries, date, overall)` → доставка (ошибка → Run error, всё
   delivered=0, элементы не seen — без изменений).
8. `MarkDelivered` по темам (log-only ошибки — без изменений).
9. log.Info.

MTProto media-resolver (§4.5.1) — в шаге 4 между c и d, лимит 3/прогон общий на
run (счётчик в pipeline).

### 4.9. Частичный сбой — семантика Этапа 8 сохраняется

Сбой темы = пропуск темы в оглавлении, её элементы не seen (НО кеш
message_state остаётся — повторный прогон досчитает без повторных LLM-вызовов
по обработанному). Сбой доставки оглавления = ошибка Run, слот не отмечается.
Ошибки после доставки — log-only. Реклама/дубли seen сразу (§4.2) — они не
доставляются, «потерять» их нельзя. `failed`-статусы message_state не
блокируют следующий прогон (элемент не seen → пересоберётся).

**Отклонения от плана и решения диспетчера (не «чинить» без триггера):**

1. **Два Upsert-батча на тему (A, затем B)** вместо одного «A(+B)»: крах
   между батчами теряет только дедуп (деградация «все primary»),
   классификация сохранена — инвариант 9A M1.
2. **Degraded-кластеры НЕ персистятся и НЕ seen** (фикс medium-находки
   ревью): in-run исключение дублей — для всех валидных кластеров (offline-
   дедуп §4.7 видим в дайджесте прогона), но строки dropped_dup + seen —
   только для кластеров, где ВСЕ члены не-degraded. Причина: offline
   Degraded=true всегда (9A п.5) — персистенция навсегда зафиксировала бы
   offline-дедуп (два разных поста одной рубрики с равным заголовком → один
   потерян даже после добавления API-ключа); онлайн-сценарий «degraded
   primary позже = ad + дубль уже seen → событие исчезает ЦЕЛИКОМ» закрыт.
   Осознанный размен: дубль degraded-кластера может быть показан в следующем
   прогоне («дубль виден» вместо «элемент потерян»).
3. **Критерий пропуска B шире буквы тест-кейса 3 плана**: в B не участвуют
   ВСЕ закешированные (done/dropped_*) независимо от cluster_id (план:
   «cluster_id≠'' → пропускаем»). Суперсет, согласуется с §2 (кросс-прогонный
   дедуп вне этапа); подтверждено диспетчером как финальное.
4. **Пересечение между кластерами → второй кластер отброшен ЦЕЛИКОМ** (не
   только пересекающийся индекс): частично-пересечённый кластер имеет
   неоднозначный primary; зафиксировано тестом.
5. **`{"clusters":[]}` — валидный ответ без повтора** (отличие от правила
   9A №8 про пустой items: отсутствие дублей — нормальный исход B).
6. **cluster_id '<runID>:<n>'** — n по списку ВЫЖИВШИХ (после guard)
   кластеров, детерминированно.
7. **Guard контракта Deduper** (dupClusterValid, паттерн L4 вызова A):
   индексы вне 1..n / дубли внутри кластера / Primary ∉ Indices → кластер
   отброшен целиком + log.Error, не panic — третья реализация или баг
   валидатора не роняют сервис.
8. **chooseDupPrimary: zero Published = «позднейшая»** — бездатный элемент
   (RSS без pubDate) не выигрывает первичность по критерию «самая ранняя
   публикация»; две zero → полный текст → меньший SourceID.
9. **Offline: пустой normalizeTitle не кластеризуется** (защита от слипания
   безымянных постов).
10. **Dup-ключи в общем потоке MarkSeenBatch с ad** (переименован adKeys →
    droppedKeys, seen ДО доставки); **сбой B-upsert → откат in-run дедупа**
    (все primary, никто не seen — без персистентного dropped_dup делать seen
    нельзя: элемент был бы потерян).
11. **Шаг 4c автоматически получает только primary** — ссылки дублей не
    классифицируются (E) и не fetch'атся: экономия бюджета 9B без правок
    links.go.

| Риск | Митигация | Триггер пересмотра |
|---|---|---|
| Прогон долгий (последовательные LLM-вызовы + fetch) | оценка ≤5–6 мин (§4.8); кеш message_state/link_cache | прогон >10 мин → режим «экономный» (§4.8 альт. 1), затем параллелизм тем (альт. 3) — порядок фиксирован |
| LLM не держит JSON в больших батчах (A на 60 элементов) | чанки по 60, fence-strip, 1 повтор, fallback extractLead | >30% фолбэков за неделю (§7 Этапа 8) → «строка на элемент» с префиксами классов |
| Реклама просачивается / ложные срабатывания | best-effort, граница §2; class хранится — ручная правка UPDATE'ом возможна | систематические жалобы → второй классифицирующий проход по ad-кандидатам |
| Дедуп не ловит переписанные новости | лид 200 рун, дата в промпте | жалобы → лид 400 рун; кросс-прогонный дедуп по digest_items последних 7 дней |
| Fetch страницы сломан (JS-рендер, paywall) | деградация kind=unavailable, сообщение остаётся | массовый unavailable по важному источнику → POST_MVP readability-эвристики |
| FloodWait на MTProto download/re-upload | лимит 3/прогон, backoff+jitter в клиенте, раз в сутки | FLOOD_WAIT в ежедневных логах → лимит 1 или отказ от mtproto-медиа (ссылка на источник) |
| RAM: sendPhoto-upload/download на 458 MB | стриминг на диск, ≤2MB fetch-тела, никакого декодирования картинок в памяти | OOM в dmesg → лимит fetch-байт 1MB, re-upload через URL-прокси отклоняем (секреты) |
| file_id протухает/невалиден ( Bot API file_id живёт, но перестраховка) | ошибка sendPhoto → ack «Не удалось показать фото», элемент жив | регулярные ошибки → пере-запрос file_id (resolver по dedup_key) |
| digest_items/message_state/link_cache растут | single-user, объёмы малы | БД >200 МБ → retention N дней (триггер Этапа 8 наследуется) |
| Старые кнопки (L2:/L3:) на доставленных сообщениях | alias'ы §4.6, golden-тесты legacy-путей | alias-рендер сломан на реальной старой строке → фикс, не удаление alias'ов |
| URL-кнопка + callback-кнопка в одном ряду (Bot API допускает) | рендер детерминирован, тесты markup | «can't parse» ошибки кнопок → раздельные ряды |
| caption-лимит 1024 байт vs полный текст | caption = сжатое саммари, полный текст — в L3 (текстовое сообщение) | — (проектное решение) |

## 8. Порядок сдачи и оценка reviewable-размера

1. **PR 9A** (~1100–1400 строк с тестами): миграция v5 + message_state +
   классификация + саммари сообщения. Самый фундаментальный — ревью особенно
   внимательно к транзакциям батчей и кеш-семантике (повторный Run = 0 вызовов).
2. **PR 9B** (~900–1200): linkfetch-пакет + ссылки. Ревью: лимиты байт/таймаутов,
   «не ретраим 429», кеш.
3. **PR 9C** (~500–800): дедуп. Маленький и изолированный.
4. **PR 9D** (~1300–1500): навигация + агрегация. Если diff >~1500 — расщепить
   по границе «рендеры+llm-агрегация (без поведения)» / «колбеки+wiring+pipeline»
   (паттерн C1/C2 Этапа 8). Ревью: байтовые бюджеты, legacy-alias'ы, guard 4096.
5. **PR 9E** (~1000–1400): медиа. Ревью: FloodWait/RAM (стриминг на диск),
   deleteMessage-гигиена, caption-лимиты.

Между PR — финальный зелёный прогон в основной сессии и актуализация доков
(TECHNICAL_PLAN §7/§9 — только своя часть). Деплой на VPS — после каждого
подэтапа по желанию пользователя (каждый подэтап самостоятелен, §5); схема v5
применяется на прод-БД при первом же деплое 9A (миграции идемпотентны;
откат не предусмотрен — дамп `state.db` перед деплоем, как в Этапе 8).
